# Unified Extension Center P0 product specification

Status: implemented release candidate — publication remains blocked by the released-Host and outer acceptance gates below

Implementation snapshot (2026-08-26): the independent project implements the signed offline Store, strict Host/Client RPC, lead-only public discovery and catalog-signing tooling, normalized three-kind inventory, immutable plans and separate loopback decisions, operation journals, typed lifecycle providers, cold recovery, existing-first local Capability RAG, an opaque task acquisition surface, trusted MCP configuration, task approval queues, and original-task continuation binding. The immutable published rc.2 browser lane remains read-only and passes as the negative Host baseline. The separate local DSH HEAD supplies the six owner surfaces for writable integration work, but it is not a published compatibility target. A deployed signed remote revision with independently produced admission receipts, a packed local-HEAD writable browser lane, an unmodified future release lane, real-provider task evidence, and ordinary-user usability remain unproven until their receipts pass.

## Problem

DSH exposes the mechanisms behind three extension families but no ordinary-user workflow across them. Profile Plugins are package-manager dependencies and Bundle layers, MCP servers are configured `dsh-mcp-client` instances, and Skills are contributions from a layered provider registry. A user must currently understand pnpm, Profile composition, Cordis rows, filesystem roots, credentials, and restart behavior to distinguish “present on disk” from “usable by this Agent.”

The existing surfaces deliberately stop short of unified mutation. Plugin Inventory is a point-in-time Loader projection without provenance or actions, Plugin settings edits only namespaces exposed by already mounted Host plugins, and `dsh plugin` forwards arguments to pnpm before reconciling Bundle membership. These are correct low-level owners, but they do not provide one discover, install, configure, update, uninstall, verification, and recovery path.

Flattening the three families into one “installed” switch would make the product less truthful. A Skill changes model instructions and may reference resources, an MCP server starts a host process or sends tool data to a remote origin, and a Plugin runs third-party code in the DSH Host or browser. Their sources, scopes, effective-state evidence, credential risks, and rollback mechanics differ.

## Proposal

Build and release a local, single-user **Unified Extension Center** as an independent community plugin project. Users install its published Bundle into a normal DSH Web Profile. P0 exposes two first-class acquisition entrances. In the Agent-assisted path, the Agent detects a task capability gap, checks what the current Agent can already use, retrieves a small evidence-backed candidate set from an admitted catalog, initiates one exact acquisition request, waits for separate human confirmation, verifies the owning runtime, and continues the original task. In the user-directed path, the person opens an Extension Store to browse, search, filter, compare, and acquire from that same admitted catalog without first creating an Agent task. Both paths converge on one inventory, immutable-plan transaction engine, owner evidence, operation journal, and receipts; the Store also exposes configuration, exact update, uninstallation, and recovery without editing YAML or running pnpm manually.

P0 unifies the entry point, state language, trust explanation, operation journal, and receipts. It does not unify the lifecycles of Skills, MCP servers, and Profile Plugins. Existing mechanisms remain authoritative: the Skill provider registry owns effective Skill visibility, the MCP client owns connection and tool registration, and Profile packages, Bundle ordering, Loader, and real boot own Plugin state. The center records operations and recovery points without becoming a second source of extension truth.

The product promise is narrow: a local user can either state a task once and let the Agent find and request one missing admitted capability, or deliberately select an eligible extension in the Store. After one exact human grant, the owner acquires and verifies it. A task-originated flow then uses it and finishes the original task; either path can later configure, verify, deliberately update, uninstall, enable or disable where the real owner supports those actions, or return to the exact prior DSH-managed state after failure. Every unverified claim remains visibly unverified.

For this product, writable P0 is the five-stage lifecycle, not an implementation milestone called “inventory plus install.” A read-only rc.2 preview may ship independently, but it is not accepted or marketed as writable P0; a partial writer that cannot configure, update, uninstall, and recover its admitted candidates remains blocked.

### Project and repository boundary

- The product source, catalog, transaction engine, recovery executable, Host code, Client code, tests, documentation, CI, package version, security policy, and releases live in the independent `dsh-plugin-extension-center` repository.
- The separately released community `dsh-capability-resolver` remains a read-only prototype and protocol reference; it is not widened into an installer. The Extension Center's packed Bundle must contribute a compatible resolver face itself so a fresh ordinary-user install does not depend on first discovering and installing a second plugin. Any reused package is pinned and shipped as an artifact dependency of this independent project.
- One published package declares `dsh.bundle.patch` and its Web Client export. It is installed, updated, and removed with the ordinary `dsh plugin --profile web ...` path; it is not copied into the DSH monorepo or a shipped DSH Bundle.
- The DSH repository does not own an Extension Center page, catalog, provider implementation, operation journal, product release, or compatibility claim. The plugin identifies itself as a community project and never implies DeepSeek endorsement.
- The plugin consumes only published DSH package exports and supported Cordis, Profile Bundle, Host, RPC, and Client extension points. It never imports DSH workspace source paths, patches built-in Web code, or requires a sibling DSH checkout at build or runtime.
- If P0 needs a missing Host capability, that capability is proposed separately in DSH as the smallest generally useful API with this external plugin as its real consumer. The product implementation and release remain in the independent repository, and the plugin supports only DSH releases that actually publish the required API.
- The center never updates, disables, or removes its own Bundle. Its lifecycle remains under the generic DSH CLI so a broken control plane can be removed without loading it.

### P0 host compatibility decisions

- `dsh-v0.1.1-rc.2` is the audited negative baseline, not a writable-P0 compatibility claim. It requires Web Client packages to use a lazy-CJS factory while its `clientBundle` preset is not published, so the independent project owns a version-pinned build configuration and proves the packed Client in a real browser. This is sufficient for an exact-release read-only preview, not for the full lifecycle below.
- Host and Client communicate over a plugin-owned, versioned, loopback-only Connection RPC channel. The channel, wire validation, and disposer ship in the same Bundle; no product namespace is added to DSH's `api-remotes` assembly. If a P0 operation cannot be carried by the published Connection API, that operation remains blocked until DSH first releases a general out-of-tree contribution API.
- The published rc.2 `dsh plugin` path is a pnpm forwarder followed by Bundle reconciliation and publishes no exclusive Profile transaction. The separate local DSH HEAD now provides a general Profile generation owner that revision-fences, stages, validates, commits, acknowledges boot, and restores last-good state; the independent plugin consumes it without importing workspace source. This implementation does not become a compatibility claim until those packages ship in an exact DSH release.
- Profile restart remains an external launcher action in P0. The center records `restart-required`, shows the exact consequence, and verifies the next reconnect; it neither kills nor supervises its own Host. Generic Plugin disable/enable is `unavailable(reason)` until a stable Host owner exists and is not required for the five-stage lifecycle.
- Published `dsh-v0.1.1-rc.2` persists Session history but has no generic durable continuation owner. The local DSH HEAD now binds a single-use claim to the original Session and user-message reference, re-checks cancellation and supersession, and dispatches the same continuation message id at most once after exact verifier evidence. This is an at-most-once dispatch guarantee, not an exactly-once task-completion claim, and it remains a release gate until published.
- On published rc.2, `ctx.skills.snapshot()` publishes merged winners and `dsh-mcp-client` publishes tools but no dynamic connection mutation owner. The local DSH HEAD now provides a revision-fenced dynamic connection owner with desired/observed state and qualified Tool-generation evidence. P0 manages only a connection to an exact Host-preprovisioned unauthenticated runtime; it does not download, install, update, or own the catalog server package. Authenticated MCP remains blocked until a formal credential-reference owner is published.

### Target user

- A person running `dsh web` on their own computer who controls the current Harness home and Web Profile.
- A person who knows the outcome they want but should not need to understand pnpm, Cordis Loader rows, patch layers, or Skill roots.
- A person willing to approve visible code, process, network, and credential risks, while secret values and internal configuration syntax remain hidden.

P0 does not target remote administrators, shared multi-user Hosts, organization policy owners, or extension developers.

### Two first-class acquisition journeys

Neither journey is a fallback. They share the same admitted catalog revision, eligibility policy, lifecycle owners, Host-owned transaction engine, inventory, and receipt schema, so an item acquired in one journey is immediately managed by the other. Each action receives its own immutable plan. Only actions with the same candidate, scope, operation, and desired state are required to have the same canonical mutation and authority payload.

#### A. Agent-assisted task journey

1. The user asks for an outcome in ordinary task language and does not need to name an extension, resolver, store, package, or install command.
2. Before claiming the task is impossible, the Agent derives a local `CapabilityNeed` and checks the Tools and Skills visible to the exact current Agent scope. If an existing capability satisfies the need, the Agent uses it and does not contact the catalog.
3. If a gap remains, the Agent invokes the read-only resolver. The Host searches a local index over one fresh admitted catalog snapshot; the raw task, Session identifier, workspace content, cookies, and credentials never enter a catalog request.
4. The resolver returns `acquisition-candidate` only when one exact candidate passes compatibility, authority, configuration-readiness, lifecycle, freshness, and evidence policy. Materially different ties return `choice-required`; unadmitted web results remain `external-only`.
5. The Agent may call `capability_request_acquisition` with only the resolver-minted `resolutionId`, opaque `candidateRef`, and single-use `continuationId`. It cannot supply a package name, URL, command, configuration body, or secret.
6. The Host re-resolves those identifiers against the same catalog and inventory revisions and mints an immutable plan. A loopback browser shows the exact source, revision, integrity, target scope, complete authority delta, initial configuration, restart behavior, checks, rollback limit, and plan hash. No artifact fetch, credential resolution, execution, file write, process start, or Profile mutation occurs yet.
7. The human confirms or rejects that exact plan. The Agent cannot call the confirmation RPC, reuse the grant, broaden it to future versions, or turn task intent into approval.
8. After confirmation, the owning provider acquires and verifies the extension. A Skill or MCP path re-reads the official winner or Tool generation before returning to the Agent. A Plugin commits through the required Profile transaction owner and remains `restart-required` until an external launcher restarts and the exact declared consumer is observed.
9. For a live Skill or MCP contribution, the next model step re-reads current capabilities and continues the same user turn. For a Plugin restart, the generic DSH continuation owner must dispatch the bound continuation message in a new turn at most once after re-checking the durable claim; without that published Host capability, the flow honestly stops at `restart-required` and cannot satisfy full P0.
10. The Agent actually uses the newly visible capability and completes the original task. Installation success, runtime visibility, continuation, and task success are recorded as separate facts.

#### B. User-directed Extension Store journey

1. The user opens the first-level **Extensions** destination without creating an Agent task; **Store** is its default view. It also exposes **Installed**, **Updates**, and **Activity & Recovery** over the same inventory and journal.
2. The user browses curated outcome categories or searches and filters by Plugin, MCP, or Skill; compatibility, source class, target scope, configuration readiness, authority, and lifecycle availability are first-class filters. Search text is evaluated against the local catalog index and is not sent to an origin or analytics service.
3. Result cards distinguish eligible, already installed, unavailable with a reason, and `external-only`. Manual selection can choose among multiple eligible trade-offs; it cannot override compatibility, trust-root, integrity, lifecycle, or policy rejection.
4. The user opens details and may compare up to three candidates. The comparison shows publisher and upstream source, catalog admission revision, exact artifact or content revision and integrity, included components, DSH range, platform and external prerequisites, configuration and credential readiness, authority and data destinations, restart behavior, complete lifecycle availability, verification evidence, retained data, and every unknown claim.
5. The user selects one exact candidate and scope. The Host derives a Store `AcquisitionIntent` and immutable plan under the same schema and policy as the task journey, and the user confirms or rejects it. The operation or desired state may differ—for example, manual MCP Install is distinct from Enable while the admitted task composition requests `install` with `desired=enabled`. A Store-originated operation has no `continuationId` or task receipt unless the user explicitly launches a new task afterward.
6. The owning provider executes and verifies the plan. The Store keeps materialization, runtime state, current-Agent visibility, and verification level separate; a completed download or write never becomes `active` by itself.
7. The installed item appears immediately in **Installed** with Configure, Verify, Update, Enable, Disable, Uninstall, Restore, or Purge shown as `available`, `unavailable(reason)`, or `external(read-only)`. **Updates** shows only exact observed targets and never applies one automatically.
8. The Store remains fully usable with model tools disabled. Acquiring the same item later through a task short-circuits to `use-existing`; task and Store paths never create duplicate material, owners, grants, or receipts.

## P0 product scope

### Unified inventory

Every row shows the extension kind, display name, owner, source, exact current version or content revision when observable or `unknown(reason)`, one observed exact update target when available, target scope, desired state, effective state, health, restart requirement, latest verification, latest error, recovery availability, and each lifecycle action with its availability reason. The view identifies visibility only for a named published observation scope; without one it reports Agent visibility `unknown` rather than treating Profile-global presence as availability.

Plugin inventory keeps dependency presence, Bundle membership, Loader configuration, effective enablement, and Fiber phase as separate facts. A Loader row is never labeled installed. A Plugin-owned Skill or MCP server appears as a child only when an explicit center adapter or receipt declares that relationship and the named runtime contribution is observable; rc.2 does not expose authoritative Fiber-to-tool or Fiber-to-Skill attribution. Every other possible child shows `owner: unknown` and remains external rather than being inferred from a name.

Items created by the CLI, external files, another Plugin, bundled providers, custom Skill roots, or runtime registration remain visible but read-only in P0. The center mutates only objects for which it owns an operation journal and recovery point. The Extension Center itself is a system item and cannot update, disable, or remove itself.

### Dual-entry discovery and Extension Store

Task-driven discovery and user-directed Store discovery are equal P0 entrances. The Agent path begins only after an ordinary task exposes a capability gap; it is not background surveillance. The standalone **Extensions** destination opens the Store by default, does not require an Agent task, and provides Store, Installed, Updates, and Activity & Recovery as its first-level views.

The Store browses curated outcome categories and searches name, capability, publisher, and tags. It filters by kind, DSH and platform compatibility, source class, scope, configuration readiness, authority, and lifecycle availability; it compares up to three candidates across kinds. Browse, search, filtering, ranking, and comparison operate on the local admitted snapshot with no query telemetry or network fallback. Missing comparison fields display `not-declared` rather than disappearing.

Both entrances use the same evidence order:

1. qualified Tool schemas and the official merged Skill catalog for the exact current Agent scope and working directory, used by the Agent for the mandatory existing-first short circuit and shown by the Store as installed or currently visible;
2. center-owned inventory and official owner evidence for material that might be present but broken, disabled, shadowed, stale, or not visible to that Agent;
3. one signed, versioned admitted catalog snapshot fetched from a configured allowlisted origin and matched locally; and
4. an explicit user-supplied URL, fetched only after the user asks to review that URL and shown as an `external-only` lead. Arbitrary Web and community discovery exists only in the catalog-ingestion plane, never in runtime task or Store retrieval.

An allowlisted origin and a self-reported digest are not a trust root. The Bundle ships `catalog-root` metadata and one signed bootstrap snapshot for offline Store use. Root metadata contains the catalog id, trusted public-key ids, threshold, minimum acceptable revision, and maximum age. Every canonical snapshot envelope contains its monotonic revision, issued and expiry times, entries digest, previous-revision digest, signing-key ids, and threshold signatures. The Host verifies the threshold, keys, canonical digest, monotonic revision, previous-revision link, expiry, and configured catalog id before indexing. Root-key rotation, revocation, or a higher minimum revision enters only through a newer integrity-pinned Extension Center release; a catalog payload cannot add its own trust key. An invalid signature, unknown or revoked key, digest mismatch, revision rollback, broken chain, or expired/frozen snapshot yields `discovery-unavailable`. The bootstrap or an unexpired verified last-good snapshot may be used only while it still satisfies the bundled root metadata.

The independent project builds its catalog as an opinionated DSH subregistry. Its ingestion pipeline may retrieve metadata from the Official MCP Registry, exact npm and GitHub releases that declare DSH compatibility, Agent Skills-compatible public registries and repositories, maintainer submissions, and community issue/activity signals. It normalizes claims, records publisher and license, pins an exact artifact or content revision, scans manifests and lifecycle scripts, derives authority, exercises compatibility and verification fixtures, and publishes the signed immutable revision. An upstream listing is only a lead. It cannot become a writable candidate until the DSH-specific lifecycle record is admitted.

Runtime task matching is a local Capability RAG pipeline. The Agent derives a bounded `CapabilityNeed` containing outcome, input/output modality, scope, platform constraints, required data access, and maximum authority. The resolver searches normalized outcome tags, provided Tools or Skills, compatibility, configuration readiness, authority, source freshness, and lifecycle completeness, then hydrates only a small eligible shortlist. The Store searches the same normalized records but allows the person to compare all eligible matches instead of requiring one model-selected winner. Full READMEs, Skill instructions, catalog shell strings, and community posts are never treated as model instructions. The need and Store query text do not enter a catalog URL, request body, header, analytics event, or second model request.

Deterministic policy filters precede model choice or Store acquisition. Task-resolution results are:

- `use-existing`: one current Agent-visible capability satisfies the need; no catalog or mutation is required;
- `management-required`: existing material is not currently usable and owner evidence identifies one exact human-managed configure, enable, update, or restore action;
- `acquisition-candidate`: one materially superior, writable, exact candidate is eligible;
- `choice-required`: two or more candidates differ materially in authority, data destination, scope, cost, or outcome;
- `no-eligible-candidate`: a fresh and complete observation found no admitted candidate;
- `discovery-unavailable`: current scope, catalog freshness, network/cache, or policy evidence is incomplete; and
- `external-only`: a source was found but has not passed catalog admission.

Store cards show name, kind, one-sentence outcome, publisher, exact revision, compatibility, component summary, authority summary, and current state. Detail and comparison add the full artifact identifier, digest, source, component and Tool list, context-cost estimate when measurable, Host/OS/runtime and extension dependencies, scopes, install-time versus runtime authority, configuration/credential prerequisites, overlap and hard conflicts, signature status, lifecycle availability, and evidence. Candidate copy, popularity, downloads, stars, reviews, and catalog badges remain third-party or community claims. They may support curation or tie-breaking but never create installation eligibility. The UI separately labels upstream source, catalog admission, artifact pinning, compatibility, authority, runtime evidence, and task evidence; none means secure or officially endorsed. A stale, incomplete, or failed observation cannot become a successful empty result or mint an acquisition plan.

P0 is a controlled Extension Store and acquisition service, not an open publishing marketplace. Ratings, payments, popularity ranking, arbitrary publishing, bulk updates, and community governance are excluded. The evidence and comparison behind these decisions are recorded in [Capability discovery and Extension Store research](capability-rag-research.md).

### Full lifecycle management

Discovery, installation, configuration, update, and uninstallation are first-class P0 stages rather than aliases for one generic CRUD API.

| Stage | Ordinary-user result | P0 requirement |
|---|---|---|
| Discover | Find an existing usable capability or an admitted candidate from the original task or manual search | Search the exact Agent scope before the local catalog index; return explicit freshness/completeness and decision semantics; show upstream evidence, admission revision, compatibility, authority, exact version or revision, and whether each later action is available |
| Install | Establish a center-owned extension and its recovery point | Acquire or register only exact admitted material, create the owner-specific record, validate initial configuration, journal every mutation, and withhold `active` until the real consumer proves it |
| Configure | Change supported behavior without editing YAML or files | Use a staged draft with Save and Discard, revision fencing, owner validation, secret references rather than values, an immutable plan, and a receipt for every committed change |
| Update | Move deliberately to one exact admitted target | Run only after explicit user selection; compare artifact or content, dependencies, scripts, authority, release notes, configuration schema, and migration result; retain the old usable state until the new state is proved |
| Uninstall | Stop the extension and remove what the center owns | Withdraw runtime contributions first, remove only center-owned rows, files, dependencies, and artifacts, offer separate retention or purge choices where ownership permits, verify absence, and disclose remote or owner data that remains |

Enable, disable, restore, and permanent data purge are supporting write operations with their own plans and receipts. `verify` only refreshes owner evidence, creates no mutation plan, and never calls an arbitrary MCP tool. `rollback` is an internal failed-transaction phase; the user-facing recovery action is `restore`. P0 has no generic `repair` action: the UI must resolve a proposed repair to configure, update, enable, or restore before planning. Inventory exposes every action as `available`, `unavailable(reason)`, or `external(read-only)`, so a missing owner capability cannot be mistaken for a successful no-op.

Admission to the P0 writable catalog requires every applicable Discover, Install, Configure, Update, and Uninstall stage to be implementable and verifiable. An owner may explicitly declare that no configuration exists; that satisfies Configure without inventing a form. A candidate missing any other required owner capability may remain discoverable as incomplete or external, but it cannot produce a one-click install plan.

### Immutable plan and human confirmation

Every mutation begins with a Host-minted plan bound to the current inventory revision and a hash over its normalized content. The plan expires and is single-use. It includes:

- operation kind (`install`, `configure`, `update`, `enable`, `disable`, `uninstall`, `restore`, or `purge`), extension kind, owner, target Profile or Skill root, and desired state;
- exact artifact name, version or revision, integrity, and source;
- Profile manifest, lockfile, Bundle list, patch row, Skill file, and credential-reference mutations;
- dependency and lifecycle-script findings, Bundle manifest and patch entries, authority changes, configuration-adapter hash and version, schema digest, owner revision, normalized diff or migration result, and restart requirement;
- for MCP stdio, the exact Host-preprovisioned executable, executable digest, fixed arguments, working directory, and canonical user-selected roots; for HTTP, the canonical HTTPS origin, exact endpoint, `authentication=none`, forbidden redirects, and mandatory data-egress warning; the browser and Agent can select only an opaque Host allowlisted `runtimeRef` and cannot submit a command, URL, header, environment field, or secret;
- the type-specific structural and runtime checks that will run;
- for uninstall or purge, the exact center-owned material removed, retained owner or remote data, credential-record choice, and whether recovery remains possible;
- the last-good recovery point and the limits of rollback; and
- every claim the center cannot verify.

Inside the Host, both entrances normalize into one non-submittable `AcquisitionIntent`: `origin` (`store` or `task`), extension kind and id, exact version or content revision, digest, scope, `operation`, `desired`, admitted capability set, authority delta, policy result, and idempotency key, plus an optional `continuationId` only for `task`. The Host derives it from an opaque resolver reference or a Store selection re-resolved against the current catalog; neither Agent nor browser may populate its coordinate, digest, authority, desired state, or policy fields. Its canonical mutation core is candidate, revision, digest, scope, operation, desired state, admitted capabilities, authority delta, and policy result. When those inputs match, Store and task must produce the same core and transaction mutation and verification steps; provenance fields, idempotency keys, plan ids, and plan hashes may differ. Manual Store MCP Install and task-composed MCP acquisition intentionally have different desired states and therefore do not claim intent or plan identity. The intent is not authorization; it is the sole internal record from which the Host may mint an acquisition plan.

Only a loopback Web client with the local management channel may confirm and commit a plan. Trusted-host admission alone is insufficient. The Host checks the plan id, hash, expiry, Profile revision, catalog revision, resolution, continuation, and target ownership again immediately before mutation. Catalog descriptions and install strings are data, never executable input.

P0 exposes two narrow model-facing acquisition tools:

- `capability_resolve` is read-only. It accepts the locally derived need and current observation scope. For `acquisition-candidate`, the Host returns a candidate-bound `resolutionId`, opaque `candidateRef`, and single-use `continuationId`; all three bind the same Session, user-message reference, need digest, scope, catalog and inventory revisions, expiry, and cancellation/supersession fence. Model-visible evidence is limited to closed enums, normalized capability tags, opaque ids, pinned revisions, authority flags, and one length-bounded catalog-authored factual summary. Publisher README, errors, install prose, and community text are available only as escaped browser review data. The tool never returns an executable install string.
- `capability_request_acquisition` accepts only `resolutionId`, `candidateRef`, and `continuationId`. It may ask the Host to mint a pending plan and wait for the separate loopback decision, but it has no confirmation parameter and no package, URL, command, configuration, scope-escalation, credential, update, uninstall, or recovery input.

For `choice-required`, the current task attempt closes with that terminal outcome. The comparison surface may collect a human candidate selection, but selection only creates a new task attempt, re-runs eligibility, and mints a new candidate-bound resolution and continuation id; it is not acquisition authority. The Agent must then make the normal request, and the person separately confirms its exact immutable plan.

For `management-required`, the current task attempt closes with that terminal outcome, one opaque extension reference, and exactly one proposed action from configure, enable, update, or restore. It creates no acquisition intent or mutation plan. A person may start that lifecycle action in Extensions through its normal exact plan and confirmation. Completion never reopens the terminal attempt; choosing **Retry original task** creates only a new `taskAttemptId`, retains the original Session and user-message reference, and repeats existing-first resolution. If the new attempt returns `use-existing`, that task outcome remains terminal and a separate durable Host continuation claim owns actual resumption. Activity joins the Center's strict retry binding with the exact Host claim and reports the Host states `pending`, `ready`, `consumed`, `claimed`, `canceled`, `superseded`, `expired`, or `invalid`; an interrupted reservation is `reconciling`, and an absent Host owner is `unavailable`. It never rewrites the task outcome as a continuation state. If the new attempt instead returns `acquisition-candidate`, it receives the normal resolution, candidate, and acquisition-continuation identifiers. The Agent cannot start or confirm the management action.

Calling the request tool is not authorization and causes no acquisition side effect before human confirmation. The Agent may autonomously initiate this request and, after owner verification, use the new capability. It cannot approve any mutation, invoke the loopback confirmation RPC, install through shell or package-manager tools, or initiate a standalone configure, update, enable, disable, uninstall, restore, or purge. A task-eligible MCP exception is one exact `install` plan with `desired=enabled`, whose complete zero-secret configuration and authority are already in the admitted candidate and confirmation; the disabled row is only a staging phase, and the receipt separately records register, configure, connect, and verify. It does not grant a reusable Enable operation. Other lifecycle operations remain human-started in the management surface.

When capability preflight does not find every required writable Host owner, the read-only preview does not register `capability_request_acquisition`; Store acquisition controls render `unavailable(host-capability)` and the Host cannot mint an acquisition intent or plan. A model-callable tool that merely fails later is not an acceptable read-only preview.

### Task acquisition and continuation

Agentic acquisition uses a state machine separate from the extension operation journal. Its mutable phase is `checking-existing → resolving → awaiting-approval → acquiring → verifying-visibility → restart-required | ready-to-resume → resuming`; it closes exactly once with a terminal outcome of `use-existing`, `continued`, `choice-required`, `management-required`, `no-eligible-candidate`, `discovery-unavailable`, `external-only`, `rejected`, `canceled`, `recovery-required`, `resume-conflict`, or `failed`, plus a bounded reason. A terminal task record never transitions again. An extension operation may succeed while the task outcome is `canceled` or `resume-conflict`; neither record overwrites the other.

The one-click task path has stricter admission than manual management. The candidate must have an exact artifact or content revision and integrity, a compatible released DSH range, deterministic zero-secret initial configuration, no unresolved external runtime or credential, no lifecycle scripts, a known authority delta, one target scope, a complete owner-backed lifecycle, and a deterministic runtime visibility recipe. Anything requiring a user choice, secret, arbitrary executable, unreviewed URL, or materially broader authority returns `choice-required` or `external-only` and cannot be silently defaulted.

The Host mints the secret-free, single-use `continuationId` as part of the candidate-bound resolver response, before the Agent can request acquisition. It initially binds the original Session and user-message reference, derived-need digest, observation scope, catalog and inventory revisions, selected candidate, expiry, and cancellation/supersession fence; the Host later binds the accepted plan and operation identifiers plus expected runtime evidence without changing the id. It does not copy the raw task or catalog prose. Wrong-session, wrong-resolution, expired, replayed, canceled, or superseded claims are rejected. Before resume, the Host proves that the operation succeeded, the expected contribution is visible to the exact Agent scope, the source task is neither canceled nor superseded, and the claim has not been consumed.

Skill and MCP acquisition may continue on the next model step only when their published owners make the new winner or qualified Tool generation visible to the current Agent. Plugin acquisition always requires the real external Profile restart. Full P0 requires a generic DSH continuation owner to open a new turn from the durable claim and dispatch the bound continuation message at most once after reconnect and authoritative cancellation/supersession re-checks. Current rc.2 does not provide that guarantee; the center must end the turn at `restart-required`, preserve the claim as non-executable evidence, and require an explicit new user turn rather than claiming automatic continuation.

Task continuation re-enters capability resolution before use. It never assumes that an installation receipt proves current visibility, and it never replays the acquisition request. The original task becomes `continued` only after the new capability is actually invoked; it becomes task-verified only after the task-specific external observable passes.

### Type-specific lifecycle mapping

| Kind | Discover | Install | Configure | Update | Uninstall | Effective `active` evidence |
|---|---|---|---|---|---|---|

Plugin P0 accepts only fixed versions from the allowlisted registry. Moving tags, arbitrary Git URLs, local paths, user tarballs, and packages whose dependency graph requires `preinstall`, `install`, `postinstall`, or `prepare` scripts are refused by the one-click path. A Plugin update is a fresh approval, not continuation of its install grant. A writable catalog candidate must either provide a plugin-owned Extension Center configuration adapter or explicitly declare that it has no user configuration. The adapter keeps the owner UI, validators, credential controls, and revision but hands the normalized diff to the Host-minted plan before save. An existing settings card without this adapter is an `external(read-only)` link, not center-managed Configure. Configuration never falls back to raw YAML or a generated generic schema editor: **No configurable options** is shown only when the live owner declares that fact; a missing or unpaired namespace, card, or adapter is **Configure unavailable**. Tests use local `.tgz` fixtures as deterministic stand-ins for pinned registry artifacts; this is not a product input surface.

The Plugin configuration integration is a versioned, optional Host/Client contribution packaged with the target Plugin. It declares adapter version, target Plugin version range, schema digest, and deterministic validation or migration over the user layer and credential references; the browser owner card supplies its normalized proposed diff and live owner revision. An update plan binds the source and target artifact hashes, adapter hash and version, schema digest, owner revision, normalized diff, and staged migration result, then rechecks the live owner immediately before commit. If an installed Plugin has configuration and the staged target adapter cannot validate or migrate it before promotion, Update is `unavailable(reason)`. The adapter is effect-owned and optional to the target Plugin's core: its tool, service, and ordinary UI contributions must load without `ctx.extensionCenter` or a center Client slot. Catalog admission rejects a Plugin that makes core activation depend on the center; removing the center withdraws only its configuration integration.

Generic Plugin `disable` and `enable` are `unavailable(reason)` in P0: retaining a dependency while removing its Bundle membership is not stable under rc.2 reconciliation, and the center will not invent a second activation format. Plugin `restore` is available only through the required Profile transaction owner and reinstates the complete named rollback point—artifact, dependency resolution, Bundle order, patch rows, and owner settings. It is never treated as an alias for enable.

MCP P0 supports the existing stdio and Streamable HTTP transports and Tools only. Its managed object is the connection definition, not the server runtime: **Install** registers one center-owned connection, **Update** selects an exact Host descriptor revision, and **Uninstall** removes the connection after quiescent disposal. It never downloads, builds, upgrades, or deletes a stdio executable, and it does not claim to install or update an HTTP service. A stdio candidate can generate a plan only when its exact canonical executable path, digest, fixed arguments, and working directory resolve; user configuration may add only canonical roots. An HTTP candidate is a canonical credential-free HTTPS origin plus exact endpoint, mandatory data-egress disclosure, `authentication=none`, no custom headers or environment credentials, and a fail-closed no-redirect policy. The Host owns this strict descriptor union and exposes only opaque `runtimeRef` choices; neither the model nor browser may submit arbitrary commands or URLs. The descriptor digest is rebound through the plan, durable state, inventory evidence, journal, and receipt. Every owner request carries the exact resolved transport plus a stable Host-valid mutation id derived from `{operationId, phase, descriptorDigest}`, while the Host receipt also binds its resulting desired-record digest; any drift is refused before mutation. P0 does not auto-call an arbitrary MCP tool as a health test.

Manual Store management keeps MCP Install, Configure, and Enable as distinct user-visible lifecycle actions. A confirmed manual Install is owner-backed rather than a Center-only placeholder: it writes one strict disabled desired row through the dynamic MCP owner, verifies the exact owner revision and transport plus observed disabled state with zero Tools, and issues the normal operation receipt. Configure is a separate immutable plan that updates that owner row, while Enable is a later independently authorized plan. Task-originated MCP acquisition is a stricter composition: only an admitted zero-secret descriptor with one fixed scope and no unresolved runtime may produce one atomic `install` plan with `desired=enabled`. Its disabled row is staging, not a new lifecycle operation kind. Before confirmation there is no row write, process start, DNS, HTTP handshake, or credential resolution. After confirmation, the published dynamic MCP owner transactionally creates the disabled row, applies the exact initial configuration, starts or connects, completes `initialize` and `tools/list`, and publishes the expected qualified Tool generation. Any failure withdraws the Tool, cancels retries, quiesces the child or connection, removes the staged row, and restores prior authority state. This grant cannot be reused for later Enable, reconfiguration, a new origin, or a different descriptor revision.

Skill installation and update never execute included scripts. Confirmation shows the complete file manifest, instruction body, invocation flags, symlinks, and the presence of scripts or executable assets. An update is a manual move to one allowlisted fixed content revision; any external byte change rejects it, and P0 neither merges nor overwrites the edit. Path traversal, links escaping the selected root, malformed frontmatter, and a conflicting external revision reject before commit. Project `.dsh/skills`, project `.agents/skills`, user `.agents/skills`, custom roots, bundled Skills, and runtime provider contributions are read-only; project writes wait for an explicit published workspace/Agent selector.

### State model

The UI never compresses “requested,” “materialized,” “effective,” and “verified” into one badge.

| Field | Values | Meaning |
|---|---|---|
| `desired` | `enabled`, `disabled`, `removed` | The user's committed intent |
| `materialized` | `absent`, `installed`, `configured` | Whether DSH-managed files or dependencies exist |
| `effective` | `inactive`, `restart-required`, `starting`, `active`, `degraded`, `activation-failed`, `unknown` | What the owning runtime currently proves |
| `agentVisibility` | `visible`, `not-visible`, `unknown` | Whether the exact current Agent scope can discover the expected Skill or Tool contribution |
| `verification` | `unverified`, `structural`, `runtime`, `task` | Highest completed evidence tier |
| `rollback` | `available`, `running`, `used`, `unavailable`, `failed` | Recovery capability and outcome |
| `ownership` | `center`, `external`, `system`, `parent-plugin` | Whether this row accepts direct mutation |
| `operationKind` | `install`, `configure`, `update`, `enable`, `disable`, `uninstall`, `restore`, `purge` | The lifecycle intent of the current or latest operation |
| `updateObservation` | `unknown`, `none`, `available` | Catalog observation only; `available` includes one exact target and never changes desired or effective state |
| `taskPhase` | `none`, `checking-existing`, `resolving`, `awaiting-approval`, `acquiring`, `verifying-visibility`, `restart-required`, `ready-to-resume`, `resuming` | Mutable original-task progress before a terminal outcome |
| `taskOutcome` | `none`, `use-existing`, `continued`, `choice-required`, `management-required`, `no-eligible-candidate`, `discovery-unavailable`, `external-only`, `rejected`, `canceled`, `recovery-required`, `resume-conflict`, `failed` | Single-assignment terminal result with a bounded reason, independent from the extension operation outcome |

Operations follow `planning → awaiting-confirmation → staging → verifying → committing → succeeded`. Any staging, verification, or commit failure follows `rolling-back → rolled-back`; only a failed recovery reaches `recovery-required`. A process result records timeout, signal, and exit code independently.

Draft configuration and an observed update do not change the running extension. A configure or update operation keeps the previous material, configuration, and effective evidence authoritative until the target owner accepts the committed revision and its required runtime checks pass; failure restores that previous triple rather than publishing a mixed state.

Type-specific detail remains visible: Plugin rows retain Loader Fiber phase; MCP rows retain configured transport, last observed tool generation, and whether live detail is unavailable; Skill rows retain snapshot completeness, winning source, center-owned material state, validation, and separate model/user invocation policy. P0 never invents MCP reconnect state or a Skill loser chain that the owning rc.2 service does not publish.

### Receipts and task verification

Each operation produces a durable, secret-free receipt containing the operation kind, plan hash, source and integrity, scope, before and target states, configuration and migration result, committed DSH-managed mutations, retained data and credential choices, checks actually run, restart requirement, runtime observations, rollback point and outcome, and remaining unverified claims. Receipts survive browser refresh and Host restart.

An Agent-initiated acquisition adds a separate secret-free task receipt containing only the Session/user-message reference, derived-need digest, resolution and candidate identifiers, catalog and inventory revisions, plan/operation/continuation identifiers, human decision, visibility observation, resume outcome, and task observable. It never stores the raw user task, retrieved community prose, secret values, or model chain-of-thought. Rejection, cancellation, expiry, and replay each produce one terminal decision record without an acquisition side effect.

The center uses exact labels: **structure verified**, **isolated Profile booted**, **active in current Profile**, **MCP handshake and tool sync complete**, **Skill visible to target Agent**, and **user task verified**. No earlier label implies the later one.

Task verification is an explicit normal DSH task with an external observable selected by the user or a catalog-owned deterministic recipe. In the task-driven path it is the original user task, not a substitute “test the extension” prompt. The center may correlate its receipt to the resulting Session evidence, but it does not invent a universal oracle. Without an external result or expected call sequence, an extension remains runtime-verified and the task remains completed without a product-verified outcome.

### Recovery outside the Web UI

- Before mutation, each published operation owner records its exact DSH-managed files, hashes, Bundle order, credential references, and recovery point. For Plugin work, the required Profile transaction owner—not the center's browser or an rc.2 disk editor—creates and validates the isolated generation.
- The Profile owner promotes only a validated generation and returns a named last-good point. The running Profile still reports `restart-required` until an external launcher completes a real restart and the center reconnects.
- An interrupted transaction is resumed from its journal on the next Host start and either finishes rollback or enters `recovery-required`; it never guesses `active` from files alone.
- A fixed break-glass CLI at the absolute, receipt-pinned recovery path first queries the published Profile owner for the exact deterministic restore receipt. It verifies any committed receipt against the journal generation/tree pin and either the exact receipt after-snapshot or its single legal boot-acknowledgement successor; unrelated current-inventory drift is rejected. Only absence permits selector validation and a new last-good restore. The flow loads neither the installed package nor the Web Bundle under repair, and a lost response retry cannot advance the Profile revision twice, including after restart acknowledgement.

Rollback guarantees only DSH-managed state. It cannot revoke a remote grant, undo network requests, or reverse side effects from third-party code; the receipt states that limit.

### Independent project lifecycle

- Product-owned durable state lives outside the installed package and Profile generation under `$DSH_HOME/extension-center/`: private operation journals, secret-free receipts, the ownership manifest, and last-good recovery points have versioned subdirectories and hashes. Install and update atomically copy the built standalone recovery module to an owner-only executable at `$DSH_HOME/extension-center/recovery/<center-version>/<platform>-<arch>/break-glass.mjs`, verify its packed-artifact hash, and pin that absolute path, hash, and the canonical Host home in every journal that may need it; recovery never imports code from `node_modules`. Break-glass Host calls use only that pinned home as `DSH_HOME` in a scrubbed environment, so ambient process state cannot redirect recovery to another Profile store. The package declares no npm `bin`: the public Profile transaction owner rejects package binaries, and recovery uses only the copied hash-pinned module through an exact `node` invocation.
- The Extension Center's own inventory row is read-only and shows exact generic DSH CLI commands for install, update, downgrade, and remove. Its UI never attempts self-mutation.
- An Extension Center `vN-1 → vN` acceptance run upgrades through the generic CLI, migrates a copy of plugin-owned durable state before publication, proves Host and Client protocol versions match, and completes one real managed operation. A stale browser Client receives an explicit reload-required response and cannot commit a mutation against a newer Host.
- A failed self-upgrade is recovered outside Web by reinstalling the exact previous artifact. Product rollback code may recover extensions the center manages, but it never claims to recover its own broken package while that package is running.
- The documented generic removal path requires the center to be idle with no staging, promotion, or rollback in progress and its operation lock released. Forced external removal during an operation is external interference: the persisted journal and hash-pinned recovery executable own recovery, not a vanished browser page.
- Generic removal withdraws the Host service, Connection channel, Client graph row, styles, listeners, timers, and processes without changing managed extensions or user patches. Journals, receipts, ownership data, recovery points, and every recovery executable still referenced by them remain by default; a separate explicit purge refuses while any pending operation or retained recovery point refers to the target version.
- On reinstall, an object regains `center` ownership only when the ownership manifest, authoritative bytes, exact revision, and expected runtime owner all still match. Any object changed while the center was absent becomes `external(read-only)`; reinstall never auto-adopts, overwrites, or rolls it back.

## Trust and authority

| Kind | Authority the user grants | Required P0 disclosure |
|---|---|---|
| Skill | Instructions can change model decisions and reference local scripts or assets | Complete source, body, file manifest, target scope, invocation flags, and a statement that catalog admission is not an instruction audit |
| MCP | Stdio starts a host process; HTTP sends tool inputs to a remote origin | Exact allowlisted command or canonical HTTPS origin, fixed arguments, cwd, executable or descriptor digest, explicit zero-authentication and no-redirect policy, data-egress warning, discovered tools, and a statement that connection is not a security verdict |
| Plugin | Third-party Host or Client code runs with the current user's process authority | Exact artifact, dependency and script findings, Bundle rows, same-process authority warning, restart requirement, and a statement that runtime success is not a code audit |

Secret values never appear in inventory, plans, browser read responses, patch files, command arguments, logs, Session events, snapshots, errors, or receipts. Configuration carries references; the credential owner resolves values only for the operation that needs them. Removing an extension offers deletion of center-owned local credential records separately and never claims to revoke a remote authorization.

Untrusted names, descriptions, README text, tool schemas, and errors render as escaped text. Spawned processes receive a scrubbed ambient environment plus only explicitly approved references. Temporary directories are private, files are owner-only and exclusively created, and paths are randomized. Teardown closes notification listeners, requests graceful child shutdown, kills any child still alive after the bounded grace period, and then awaits confirmed process exit.

## Ownership and extension points

The external package declares a plugin-owned `ctx.extensionCenter` service for normalized catalog snapshots, local Store search, Capability RAG, acquisition requests, provider registration, immutable plans, operation serialization, receipts, and recovery orchestration. It is not a new DSH core Service Definition. The Bundle contributes the read-only resolver and opaque acquisition-request Tools to the exact Agent scope through normal Tool registration; confirmation remains a separate loopback Client action. Three provider implementations live in the independent repository and adapt published DSH owners rather than bypassing them: the Skill provider owns exact files while observing the filesystem provider and Skill registry; the MCP provider owns center-generated rows while observing the DSH client and required dynamic connection owner; and the Profile provider calls the required published Profile transaction owner for staging, Bundle reconciliation, commit, and generation rollback, then observes an external restart. Profile transactions, dynamic MCP connection mutation, and automatic cross-restart continuation stay unavailable on rc.2. Through the published Client extension mechanism, the package registers a first-level **Extensions** destination whose default Store view sits beside Installed, Updates, and Activity & Recovery.

The Host half requires only Connection to keep the loopback read surface available. It observes the current owner set for every read and activates the writable runtime in a Cordis child fiber injected with `profileTransactions`, `mcpConnections`, `taskContinuations`, `skills`, `tools`, and `loader`. The child publishes write services only after recovery and all provider, verifier, and Tool registrations complete against the same exact six owner instances it captured at activation. Replacement or loss during setup or later RPC work aborts that generation's signal, withdraws its write surface, waits for every tracked task to settle, and disposes its registrations in reverse order before a replacement generation may publish. A late owner activates the child automatically, and the read surface continues to report the remaining live owner capabilities throughout the transition.

Each provider owns provenance and type-specific detail plus a per-object capability map for discover, install, configure, update, enable, disable, uninstall, restore, and purge. Every writable capability supplies plan, apply, verify, and rollback or an explicit irreversible result; every unavailable or external capability supplies a stable reason. The manager supplies one-operation-at-a-time serialization per target Profile, MCP row, or Skill root, idempotency, revision fencing, event ordering, and durable receipts. Provider registration and every status contribution are Cordis effects whose disposer withdraws the rows and reaches quiescence.

The Profile `package.json`, lockfile, Bundle list, user patch, Skill roots, credential provider, Loader, `ctx.tools`, and `ctx.skills` remain the authoritative runtime state. The admitted catalog owns candidate eligibility, while upstream registries and community sources own only their claims. The operation journal owns what the center attempted and how to recover it; the continuation owner owns resumable task state. Managed Plugin Configure mounts a live owner card only through the product's versioned configuration-adapter contribution, which preserves owner fields, validators, credential controls, and revision while routing its normalized proposed diff through planning. An ordinary owner card without the adapter remains an external deep-link. MCP and Skill forms are center-owned adapters over their published configuration. The center never becomes a generic schema or YAML editor.

The package consumes the existing [Profile Bundle distribution mechanism](https://github.com/deepseek-ai/deepseek-harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/.agents/notes/implemented/architecture/2026-08-05-profile-plugin-bundles.md) and the public Client extension mechanism. It does not change DSH's built-in settings implementation, fork the Web application, or merge with [model-written temporary Cordis Plugins](https://github.com/deepseek-ai/deepseek-harness/blob/b150a551b8d465e31e418e1b2eaf5e79bbb7d28e/.agents/notes/implemented/feature/2026-07-08-self-referential-cordis-toolset.md), whose trust, ownership, and lifetime are different.

## P0 exclusions

Manual update of one center-owned extension to one exact allowlisted version or revision is in scope. The following broader or ownerless behaviors are not:

- Arbitrary npm packages, Git URLs, paths, tarballs, shell install commands, or lifecycle-script allowlisting.
- Moving tags, automatic updates, background updates, bulk actions, dependency auto-fixes, or automatic conflict resolution.
- Marketplace ratings, reviews, payments, popularity ranking, official certification, or security badges.
- Hosted semantic search or transmitting the user's raw need, Session metadata, workspace content, or credentials to a catalog, repository host, analytics service, or second model. Local Capability RAG is in scope.
- Model-approved mutation, unattended installation without the exact human decision, Agent access to the confirmation RPC, session-wide install authority, or remembered install grants. Agent initiation by opaque identifiers is in scope.
- Direct acquisition from arbitrary web/community results, user-provided URLs, catalog prose, package names, or shell commands; those sources remain `external-only` until a later immutable catalog revision admits them.
- Cross-Profile operations, remote Hosts, shared multi-user management, organization RBAC, or cross-device synchronization.
- Editing Agent Preset inline configuration or changing sandbox and permission policy.
- Skill authoring, rich-text editing, automatic upstream merges, or modifying `.agents`, custom, bundled, and runtime Skill sources.
- Project-scoped Skill writes without a published explicit workspace and Agent selector; P0 writes only its own user `$DSH_HOME/skills` entries.
- MCP Resources, Prompts, OAuth orchestration, remote grant revocation, or arbitrary tool trial calls.
- Authenticated MCP creation on rc.2, a center-owned credential wrapper, or UI claims about unexposed connecting/reconnecting/exhausted state.
- Plugin hot enablement across Bundle membership changes or a general process supervisor; restart remains explicit.
- Direct mutation of unsupported rc.2 Profile internals or presenting the pnpm-forwarding CLI as an atomic transaction/generation owner.
- A complete Skill loser or precedence graph; P0 observes the official merged winner and whether its own exact entry wins.
- Automatic adoption or mutation of CLI-, file-, runtime-, or Plugin-owned extensions.
- A claim that catalog admission, artifact pinning, runtime activation, or task completion proves code safety.
- Adding Extension Center product packages, UI, catalog data, or release machinery to the DSH monorepo.
- Forking, copying, or patching built-in DSH Web components instead of using published extension points.

## Alternatives considered

**Implement the center inside the DSH monorepo.** This would couple product iteration, catalog policy, release cadence, and community trust decisions to DSH core. The independent Bundle is the product; DSH remains the host and publishes only generally useful extension points.

**Fork or patch the DSH Web application.** That can produce a screen quickly but makes every DSH update a merge exercise and bypasses the supported Client plugin lifecycle. P0 registers through published extension points and declares unsupported DSH versions instead of patching them.

**Put one generic CRUD interface over every extension.** This makes implementation look smaller while erasing the facts users need: Profile restart, MCP process and network authority, Skill scope and shadowing, and parent-Plugin ownership. The proposal unifies navigation and operations while preserving type-specific providers and evidence.

**Expose the existing `dsh plugin` pnpm forwarder through a Remote.** Forwarding arbitrary package-manager arguments from the browser would bypass source admission, immutable planning, build-script policy, staging, revision fencing, and recovery. The Profile provider may invoke the same package manager only inside a bounded transaction over resolved artifacts.

**Let the Agent browse the web and run an install command.** This appears autonomous but lets untrusted prose choose code, process, network, and instruction authority, leaks task context to arbitrary sources, and makes replay and recovery unprovable. P0 lets the Agent discover and initiate, but only an admitted opaque candidate can reach a Host-minted plan and only a loopback human can authorize it.

**Require the user to browse the catalog before every task.** This reproduces marketplace friction and assumes the user already knows the missing capability. The Agent-assisted path starts from the task, checks existing capabilities, retrieves a narrow candidate set, and returns to the same objective. The equally supported Store path remains available whenever the user intentionally wants to explore, compare, or acquire first.

**Ship inventory and installation without rollback.** A failed Plugin can prevent the Web UI that installed it from starting, and an MCP or Skill write can replace previously usable configuration. Writable P0 is therefore blocked until recovery works without the Web UI and proves the previous Profile can boot.

**Call connection or Loader activation task success.** Runtime evidence proves that a consumer exists, not that it solves the user's need. The product keeps task verification separate and accepts `runtime` as the highest honest level when no external oracle exists.

## Acceptance path

### Acceptance Red A — task-driven acquisition and continuation

Before implementation, add a keyless outer black-box scenario in the independent repository. It runs the real packed Bundle, Loader, resolver, Extension Center Host and Client, loopback RPC, browser, Skill registry, dynamic MCP owner, filesystem, Session persistence, approval/cancellation, and a deterministic script model. Only the catalog/artifact edge and model are fixtures. It begins red because the product artifact, model-facing acquisition request, Profile transaction owner, dynamic MCP connection owner, and durable cross-restart continuation owner do not exist.

1. Start an unmodified supported DSH release from an empty isolated Harness home with the packed Extension Center Bundle, no shell or generic filesystem escape tool, and no fixture Skill. The fixed catalog contains one correct Skill candidate and one decoy. The high-entropy answer exists only in the correct Skill body, never in catalog metadata or model fixture.
2. The user says only: “Using Acme Q7 on-call rules, convert alert `E17/P3` into the emergency code; output only the code.” The prompt does not mention a resolver, extension, Skill, marketplace, install, or candidate.
3. Prove the Agent checks the exact current scope first. In a separate preinstalled lane it uses the existing Skill and makes no catalog request, plan, confirmation, download, or write.
4. In the missing-capability lane, the fixed snapshot GET contains no task marker, user text, Session id, cookie, credential, workspace content, or secret. The Host verifies the pinned root, threshold signature, digest, monotonic revision, chain, and expiry before local retrieval returns a fresh `acquisition-candidate`. Model evidence contains only bounded normalized fields and opaque identifiers, never raw install strings or publisher/community prose.
5. The Agent selects the correct exact `candidateRef` and calls `capability_request_acquisition`. Before the loopback decision, external ledgers prove zero artifact read/download, extraction, credential resolution, process execution, file/Profile mutation, or restart.
6. The browser displays source, content revision, integrity, target Skill root, complete file and executable manifest, invocation policy, authority, verification recipe, plan hash, and original-task continuation intent. The browser—not the Agent—allows the exact single-use plan once.
7. The center atomically installs the Skill, then uses the official `snapshot()` and `get()` owners plus the model-invocable surface to prove the exact revision wins in the original Agent scope. The request returns `installed-and-runtime-verified` only after those observations.
8. The next model step in the same Session and turn re-reads capabilities, loads the new Skill, and continues the original task without creating or copying a new user message. The final answer equals the high-entropy Skill fixture, and Session evidence proves the Skill was absent before acquisition, present before use, and actually invoked.
9. Run `use-existing`, `choice-required`, `management-required`, fresh `no-eligible-candidate`, cold network failure, stale last-good catalog, forged or unknown-key signature, digest tamper, revision rollback, frozen/expired snapshot, malicious catalog prose, selection followed by separate confirmation, wrong-session or wrong-resolution claim, token replay, concurrent superseding task, and secret-sentinel branches. For `choice-required`, selection leaves the old attempt terminal and creates a new candidate-bound attempt before acquisition can be requested. For `management-required`, an unusable managed fixture closes the attempt with one exact human action and no acquisition intent or plan; completing that action and choosing Retry creates a new attempt that resolves existing-first. Pre-confirm rejection, cancellation, or expiry leaves every acquisition side-effect ledger at zero. Post-confirm but pre-commit cancellation may leave fetch or staging observations, but it quiesces and removes all temporary material while authoritative state remains unchanged. Post-commit task cancellation keeps the honestly installed extension and operation receipt but forbids continuation. Every task outcome is terminal once, and no query marker or secret crosses its forbidden boundary.
10. Run a same-turn task whose answer exists only behind one fixed unauthenticated streamable HTTP MCP Tool. One exact admitted descriptor contains complete zero-secret configuration and one scope. Before confirmation there is no Profile write, DNS, handshake, or Tool. After confirmation, the dynamic MCP owner atomically stages the disabled row, connects, observes the exact qualified Tool generation, and the Agent invokes it to complete the original task. Initialization failure, unexpected Tool list, cancellation, or disposal race must withdraw the Tool, connection, retry, and staged row; a later Enable requires a new human plan. This lane remains Red until a released DSH Host publishes the general dynamic MCP owner.
11. Run a black-box task whose answer is available only through a fixed Plugin contribution. After exact human confirmation, the Profile owner commits `restart-required` and a durable continuation claim. The external launcher restarts the Profile; the generic DSH continuation owner proves the exact consumer, opens one new turn from the original objective, and dispatches the bound continuation message at most once without the user resending it. Independent Session evidence must then prove task completion. Cancel, replay, supersession, failed boot, and missing-consumer lanes must not resume. This lane remains Red until a released DSH Host publishes that general capability.

The dynamic Skill and MCP lanes separately prove same-turn acquisition and use; the Plugin lane proves cross-restart task continuation. None substitutes for another. A real DeepSeek-provider variant repeats each ordinary-language task in at least three fresh Sessions without retries. Without a provider key it may self-skip, but the release receipt remains **Provider E2E Pending**.

### Acceptance Red B — user-directed Extension Store

Add a primary keyless browser black-box lane that disables model-facing tools and all external network access. It uses the packed Bundle, signed bootstrap snapshot, real Host/Client RPC, catalog verifier, transaction engine, owner registries, and filesystem. It must pass independently of any Agent task. A separate paired convergence sub-lane explicitly enables only the real resolver and acquisition-request surface in another isolated home; it does not weaken the Store-only gate:

1. From a clean Harness home, the first-level **Extensions** destination opens Store by default and exposes Store, Installed, Updates, and Activity & Recovery. A person can browse, search, filter, compare, and begin acquisition without a chat, model, API key, package coordinate, YAML, or pnpm.
2. With the network denied, the signed bootstrap snapshot provides deterministic curated categories and exact Plugin, MCP, and Skill fixtures. Search by name, outcome, publisher, and tag plus all declared filters returns reproducible results; it emits no DNS, HTTP, telemetry, or fallback search.
3. Compare three cross-kind candidates for one outcome. ### Fault injection

| Fault | Required outcome |
|---|---|
| Catalog cold-start failure, stale cache, incomplete snapshot, or changed revision | Result is `discovery-unavailable`; it is never converted to no-match, a writable candidate, or an acquisition plan |
| Forged, insufficient-threshold, unknown-key, or revoked-key signature; digest tamper; revision rollback; broken previous link; or expired/frozen snapshot | Snapshot is rejected before indexing; no candidate, intent, plan, artifact request, or last-good downgrade occurs, and the exact trust-root reason is retained |

| Kill at each prepare, stage, verify, promote, and rollback boundary | Next start deterministically completes recovery or reports `recovery-required` with the break-glass command |

## Acceptance criteria

- The product ships from an independent repository as one installable Host+Client Bundle; an unmodified supported DSH release can install, boot, update, and remove it through public mechanisms.
- No Extension Center product implementation, catalog, test fixture, or release artifact is added to the DSH monorepo. Any required DSH API change is a separate generally useful Host proposal and must be released before the plugin claims compatibility.
- `dsh-v0.1.1-rc.2` passes the negative compatibility lane only: the Profile transaction, dynamic MCP connection, and durable continuation owners are separately unavailable; no acquisition request tool, write intent, plan, mutation, connection, or resume is produced. Writable P0 cannot ship or claim compatibility until an exact released DSH Host publishes and passes all three general capability gates.
- Every center-owned Plugin Profile mutation goes through the published Profile owner, while every MCP desired-connection mutation goes through the published dynamic MCP owner. Profile restart remains an explicit external-launcher boundary. P0 neither edits unsupported Profile internals nor provides generic Plugin Disable/Enable or a restart supervisor.
- **Extensions** is a first-level destination whose default Store works without a task, model, API key, or live network. It browses, searches, filters, and compares the locally verified signed catalog, exposes all required evidence and unknowns, and shares the Host-derived intent schema and transaction engine with task acquisition. Canonical mutation and authority fields match only when candidate, scope, operation, and desired state match.
- Catalog admission requires the bundle-pinned trust root, threshold signature, canonical digest, monotonic linked revision, and unexpired snapshot. Unknown/revoked keys, tamper, rollback, freeze, incomplete evidence, and external-only leads cannot create an intent or plan.
- From an ordinary-language task, the Agent checks current scoped capabilities first, retrieves only from a fresh admitted catalog, autonomously selects at most one materially dominant candidate, and initiates acquisition only by opaque identifiers. It never invents coordinates or executes catalog/community guidance.
- Before the human confirms the exact loopback plan, every acquisition side-effect ledger is empty. Pre-confirm rejection, cancellation, expiry, stale evidence, prompt injection, replay, and a superseding task cannot install or resume anything. After confirmation but before commit, cancellation cleans and quiesces staging while leaving authoritative state unchanged; after a successful commit, cancellation retains the extension and receipt but forbids task resume.
- After confirmation, a dynamically visible Skill or MCP capability is owner-verified before a new Agent step is dispatched for the original objective. A Plugin path first crosses the external restart and exact consumer gate. The continuation owner guarantees at-most-once dispatch of the bound message; task completion is separately evidenced and is never described as exactly once.
- From the first-level Extensions surface, every Skill, MCP, and Plugin fixture completes Discover → Install → Configure → Verify → exact Update → Restore when needed → Uninstall without the user writing YAML or invoking pnpm; Skill and MCP additionally prove Enable/Disable, while Plugin exposes generic Enable/Disable as unavailable with a reason.
- Configure either reaches the live owner-backed form or displays an actionable unavailable reason; **No configurable options** appears only when the owner explicitly declares it. Every save is revision-fenced and preserves the previous runtime state on rejection.
- Every update is an explicit move to one exact allowlisted version or revision after a dependency, authority, content, and configuration-migration diff. P0 performs no automatic or background update.
- Every uninstall proves the owning runtime contribution is withdrawn, removes only center-owned material, records retained settings, data, remote state and credentials, and exposes recovery or irreversible purge truthfully.
- Every mutation requires confirmation of one exact immutable plan; no confirmation means no write, execution, credential resolution, or restart.
- Every effective-state claim comes from the official Skill registry, MCP client/tool registry, Loader, built Profile boot, or a named external task result rather than manager self-report.
- Every failed or uncommitted mutation restores the prior DSH-managed state and proves it usable; otherwise writable release is blocked and read-only inventory is the only shippable mode. Cancellation or supersession after a successful commit instead preserves the truthful extension state and receipt while preventing task continuation.
- Every secret-sentinel scan is empty, and authenticated MCP stays disabled until formal credential-reference resolution is complete.
- P0 MCP golden paths are unauthenticated and expose only configuration, official tool-generation evidence, and explicit unknown live detail; they do not claim a server runtime update or unexposed reconnect state.
- Every unknown-source, externally managed, system, parent-owned, or stale-revision mutation is refused without changing its bytes.
- At least four of five ordinary users who have not read DSH documentation start with an outcome-only task, understand the exact acquisition card, approve or reject it correctly, and reach the task result without naming an extension, editing YAML, running pnpm, or resending the task after restart. In a separate Store study, four of five enter Extensions without a task, browse or search, compare candidates, explain the material permission difference, and acquire the intended eligible item. A separate lifecycle study has the same threshold for one assigned extension's Discover → Install → Configure → Verify → Update → Uninstall journey within fifteen minutes and covers all three kinds.
- The complete flow is keyboard-operable, does not rely on color alone, returns focus to the failed action, and preserves useful failure detail across refresh.
- The independent project's focused tests, coverage, built artifact smoke, browser lane, compatibility matrix, package inspection, release smoke, and applicable real-provider lane pass with reviewed output. A separate DSH Host change, if any, passes that repository's required gates independently.

## Risks

- No released DSH Host currently satisfies the Profile transaction, dynamic MCP connection, and durable task-continuation gates, so full writable P0 delivery depends on three separate general Host capabilities. Until one exact release passes all three lanes, only the read-only resolver/Store/management preview and the `dsh-v0.1.1-rc.2` negative baseline are shippable.
- Published DSH extension points may change across release candidates. Exact peer ranges, a per-release compatibility matrix, fail-loud startup checks, and independent releases contain the impact; unsupported DSH versions remain unsupported instead of receiving source-path shims.
- An admitted, immutable catalog snapshot reduces ecosystem reach even when its ingestion pipeline watches multiple registries and communities. P0 accepts that cost so source resolution, authority, lifecycle support, and integrity remain deterministic; arbitrary web leads stay external until a later catalog revision admits them.
- A bundled trust root and offline bootstrap can expire or require emergency key revocation before the user updates the Extension Center. P0 fails closed to `discovery-unavailable`; it prefers an empty non-writable Store over accepting an unknown key, older revision, or frozen snapshot.
- Capability RAG can miss a useful extension or rank the wrong one. Existing-first search, deterministic eligibility filters, small evidence-backed shortlists, `choice-required`, and task-level proof contain the error; model confidence never widens authority.
- Cross-restart continuation can duplicate or revive obsolete work if its owner is weak. Single-use claims, cancellation and supersession fences, exact consumer re-verification, and separate task receipts are release gates; without them the flow stops at `restart-required`.
- Requiring a complete owner-backed lifecycle further narrows writable catalog coverage. A Plugin that has user configuration but lacks a compatible adapter or an explicit no-options declaration, an MCP descriptor whose executable precondition is unresolved, or an extension without a fixed update source remains visible but cannot be advertised as one-click managed.
- P0 does not acquire or update stdio MCP runtimes. This keeps the control plane bounded but means many community servers remain external prerequisites; the UI must distinguish a managed connection revision from the external executable version.
- Package-manager and Profile generation work can be slow or consume substantial disk. Progress and cancellation need explicit states, and generation cleanup cannot remove the last-good recovery point.
- A Plugin can still perform arbitrary same-user actions after activation. Staging and boot checks detect compatibility failures, not malicious behavior; the UI must not imply a sandbox that does not exist.
- MCP credentials require a new formal reference adapter. Shipping authenticated config before that path exists would violate the repository's credential doctrine and is a no-go.
- A Skill may influence a model in ways no structural check predicts. Body review, invocation flags, and task evidence reduce uncertainty without becoming an instruction-security claim.
- Concurrent CLI or manual file changes can invalidate a plan or rollback point. Revision fencing fails closed; P0 chooses refusal over merging external edits.
- A control-plane Plugin can break the Web surface it manages. The break-glass CLI and last-good generation are release requirements, not operational documentation deferred until later.
- Task verification cannot be universal. The product preserves runtime evidence and leaves task status unverified when no deterministic external oracle exists.
- Uninstall cannot erase undeclared Plugin data or revoke remote MCP authorization safely. Retention is the default outside explicit center ownership, and the receipt must make that residue visible rather than promising a clean slate.
